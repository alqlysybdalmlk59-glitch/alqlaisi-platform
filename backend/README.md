# منصة القليسي للتجارة الإلكترونية متعددة البائعين (Al-Qulaisi Platform)
## بنية الوسيط الأمني (Security Middleware) ونموذج المستخدم وصلاحيات الأدوار

تم تصميم وتطوير هذا النظام الأمني وفقاً للمواصفات والقواعد الأمنية المتفق عليها للمنصة، بهدف فرض العزل التام بين حسابات **العملاء** و**البائعين** و**الإدارة** على مستوى الخادم (Server-Side Enforcement).

---

### 1. الأدوار وحسابات المستخدمين (User Roles & Statuses)

يحدد النموذج `UserDomain` / `UserResponse` ثلاثة أدوار رئيسية غير قابلة للاختراق عبر واجهة المستخدم:

| الدور | الكود | الصلاحيات الأساسية |
| :--- | :--- | :--- |
| **العميل (Customer)** | `customer` | تصفح المنتجات المنشورة فقط، إدارة السلة، تقديم طلبات منفصلة لكل بائع، متابعة الطلبات، إدارة العناوين والملف الشخصي، وتقييم المنتجات المستلمة فقط. |
| **البائع (Seller)** | `seller` | إدارة متجره الخاص فقط، إضافة وتعديل منتجاته، التحكم اليدوي في التوافر (متاح/غير متاح مؤقتاً)، معالجة طلبات متجره فقط، ومراجعة مبيعاته وعمولات المنصة. |
| **الإدارة (Admin)** | `admin` | مراجعة واعتماد طلبات المتاجر، مراجعة واعتماد المنتجات قبل نشرها، إدارة الحسابات (إيقاف وتفعيل)، توزيع التوصيل الداخلي، وضبط نسب العمولة والإعدادات. |

حالات الحساب (`UserStatus`):
- `active`: حساب نشط ومصرح له بالعمل.
- `suspended`: حساب موقوف بقرار إداري؛ يمنعه الوسيط فوراً برمز `403 ACCOUNT_SUSPENDED`.
- `pending_approval`: حساب قيد التدقيق.

---

### 2. معمارية الوسيط الأمني (`AccessControlMiddleware`)

يعمل الوسيط `AccessControlMiddleware` كخط دفاع محيطي (Perimeter Security Layer) قبل وصول الطلبات إلى معالجات المسارات:

1. **التحقق من التوكن (JWT Token Verification):**
   - استخراج التوكن من ترويسة `Authorization: Bearer <token>`.
   - فك التشفير والتحقق من التوقيع الرقمي وصلاحية الوقت `exp`.
2. **عزل المسارات حسب الدور (Route Boundary Enforcement):**
   - مسارات `/api/admin/*`: ترفض أي مستخدم لا يحمل دور `admin` مع تسجيل محاولة التسلل في سجل الأمان `[Security Violation]`.
   - مسارات `/api/seller/*`: ترفض أي مستخدم لا يحمل دور `seller` أو `admin`.
   - مسارات `/api/customer/*`: مخصصة لعمليات العملاء.
3. **الاستجابات الموحدة ثنائية اللغة (Bilingual RFC-Standard Responses):**
   - إرجاع كود الخطأ، والرسالة باللغتين العربية والإنجليزية، والمسار، والوقت الدقيق.

---

### 3. قواعد العمل والأمان المحققة (Enforced Security Rules)

1. **عزل المستأجرين والمتاجر (Multi-Tenant Isolation):**
   - الدالة `verify_seller_store_ownership(store_id, current_user)` تضمن أن البائع لا يمكنه بأي حال من الأحوال قراءة أو تعديل بيانات أو طلبات متجر بائع آخر.
2. **عدم وجود نظام لكميات المخزون (No Stock Count / Manual Availability):**
   - كما تم الاتفاق عليه بصرامة في البند 4.3، لا توجد حقول لكمية المخزون أو عداد القطع. التوافر هو خيار منطقي `is_available` يتحكم به البائع يدوياً (متاح / غير متاح مؤقتاً).
3. **دورة مراجعة واعتماد المنتجات (Product Review & Publishing):**
   - المنتجات تمر بالحالات: `draft` -> `pending_review` -> `approved` / `rejected`.
   - لا يمكن للعميل رؤية المنتج إلا بعد اعتماد الإدارة وتفعيل التوافر من قبل البائع.
4. **فصل الطلبات بحسب البائع (Multi-Vendor Order Splitting):**
   - عند الشراء من عدة متاجر، يقوم النظام بإنشاء طلب منفصل لكل بائع، وحساب رسوم توصيل مستقلة لكل طلب.
5. **تقييم المنتجات بعد اكتمال التسليم فقط (Review After Delivery):**
   - الدالة `verify_review_eligibility` تمنع كتابة أي تقييم ما لم يكن الطلب بحالة `delivered` (تم التسليم) ومن قبل العميل الفعلي للطلب.

---

### 4. تشغيل الاختبارات الأمنية (Running Security Tests)

للتأكد من مطابقة النظام لجميع القواعد:
```bash
python3 ./backend/test_access_control.py
```
النتيجة: اجتياز جميع اختبارات التشفير، عزل المتاجر، رفض الوصول غير المصرح، واشتراطات التقييم.
